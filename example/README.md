# example — the forward test

Everything in this repo so far was validated *backwards*, against an app
that already existed. This directory is the other direction: the book app
that `hypermodular/SKILL.md` uses for its examples, drawn here first and
built here afterwards, root-down, evidence before code — rule 1 and rule 3
applied to the method itself.

It is a directory in this repo on purpose. Code that the doctrine needs
for its own verification — the code-side half of the registry check, the
"does a map plus evidence actually specify a node" question — lives
beside the doctrine, not in another repository.

Order of work:

1. maps — `APP-MAP.md` and the `MAP.md` tree — **done**, passes
   `scripts/mapcheck.py`
2. evidence — one block per criterion that crosses an edge, before any
   Swift — **done** (BookShelf, Library, BookDetail, Search)
3. code — one node at a time, parent first, each node's evidence holding
   before the next is started
4. the code-side checker, run against what step 3 produced

## What "code" means here — decided

Code that compiles and whose evidence tests pass, **macro-free**. An
Xcode project generated by xcodegen: a test app that hosts one
scenario per node, hand-wired exactly like the article's `SortScenario`
— a `log` closure, logging bindings, logging capability closures — and
surfaces the log on an accessibility element; XCUITests that drive the
scenario and assert the log with one equality. No dependency on
swift-core-flow: the example's job is to show that the method's own
article works end to end with nothing but SwiftUI, and to hand the
code-side checker real Swift. Where a node's evidence turns out to be
unassertable without tooling, that is a finding, not a reason to add
the tooling.

Illustrative Swift that never builds was rejected: it would prove only
that an agent can write plausible code from a map, which is not the
claim.

Anything the maps could not express is a finding and goes in `TODO.md`.
